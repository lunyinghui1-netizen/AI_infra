## 这节课结束时，你会做到这一件事

有人问：「我们上 128K 上下文吧，反正显存有 80G。」
你能回答：「**不行。Llama-3.1-8B 在 128K 下一个请求就吃掉 17 GB KV cache，80G 卡减去 16 GB 权重只剩 64 GB——最多同时服务 3 个人。**」

并且能说出上下文变长时**同时**发生三件坏事，以及为什么这是算术必然，不是引擎没优化好。

---

## 1. 一个请求占的显存 = 权重 + 上下文

第 1 课算的是**权重**：它是固定的，装下就行。但服务一个真实请求，显存里还有第二块，而且它随上下文线性增长：

```
显存占用 = 权重 (16 GB, 固定)  +  KV cache (随上下文线性增长)  +  少量激活/碎片
```

**为什么会「越长越慢」而不是「越长越费一点」？** 因为 KV cache 干了两件坏事，第 4、5 节分别算。

---

## 2. KV cache 是什么，为什么非要存它

生成第 N 个 token 时，注意力要回头看前面所有 token。如果每次都重算，第 N 步要算 N 份，全程 O(n²)——慢到不可用。

所以：**把每层每个 token 的 K 和 V 向量算一次就存起来**，后面直接读。计算量从 O(n²) 降到 O(n)，代价是把它们放在显存里。

这就是 KV cache。它的每 token 大小是：

```
KV cache 每 token 字节 = 2 × 层数 × KV头数 × head_dim × 精度字节
                        └ K 和 V 各存一份
```

**参数去哪查？** 不要背——去 Hugging Face 模型页的 `config.json` 里读（详细方法见 [速查文档第 2 节](../reference/kv-cache-math.md)）：

| config.json 字段 | Llama-3.1-8B |
|---|---|
| `num_hidden_layers` | 32 |
| `num_key_value_heads` | **8**（不是 `num_attention_heads` 的 32！） |
| `head_dim` | 128 |

代入：

```
2 × 32 层 × 8 头 × 128 维 × 2 字节 = 131 072 字节 = 128 KiB / token
```

**128 KiB 是什么概念？** 生成 8 000 个 token，光这个请求的 KV 就是 1 GB。这个数字下面会反复用到。

---

## 3. 算例：上下文长度 × 请求数 = KV 总量

Llama-3.1-8B（128 KiB/token）：

| 上下文 | 单请求 KV | 80 GB 卡上（减 16 GB 权重）最多并发 |
|---|---|---|
| 8K | 1.07 GB | 59 |
| 32K | 4.29 GB | **14** |
| 128K | 17.2 GB | **3** |

看到没有：**上下文翻 4 倍，并发变成 1/4。** 这不是巧合，是 `容量 ÷ KV` 的除法。

```
最多并发 = (显存容量 − 权重) ÷ (上下文 × 每 token 字节)
```

**这一条是你在评审里最有用的一句话。** 任何人说「支持 128K」，你脑子里就该自动弹出：那并发是几个？

---

## 4. 第一重代价：单请求变慢（每步要读的 KV 也变多了）

第 1 课的公式搬的是权重。现在加上 KV——**每个 decode 步骤，除了权重，还要把该请求的整个 KV 读一遍**：

```
单请求 tok/s ≈ 带宽 ÷ (权重字节 + 单请求 KV 字节)
```

Llama-3.1-8B / H100：

| 上下文 | 每步要搬 | 单请求 tok/s | 对比 8K |
|---|---|---|---|
| 8K | 16 + 1.07 = 17.1 GB | 196 | — |
| 32K | 16 + 4.29 = 20.3 GB | 165 | 慢 16% |
| 128K | 16 + 17.2 = 33.2 GB | 101 | **慢 48%** |

**同一个 token、同一张卡、同样的代码——只因为上下文长了，生成速度掉了一半。** 原因纯粹是分母变大了。这就是用户抱怨「聊到后面越聊越慢」的物理原因。

---

## 5. 第二重代价：并发暴跌 → 每 token 成本上升

第 3 节已经算了。关键在于这两件事**同时**发生：

- 单请求变慢（第 4 节）
- 能同时服务的请求数变少（第 3 节）

所以「长上下文贵」不是线性涨价，是**双杀**：摊到每个 token 上的 GPU 时间涨了，能并行摊薄成本的请求还少了。

**聚合吞吐也一起掉**（H100 / 8B）：

| 上下文 | 并发 | 聚合吞吐 |
|---|---|---|
| 8K | 59 | 约 2 490 tok/s |
| 32K | 14 | 约 616 tok/s |
| 128K | 3 | 约 149 tok/s |

> 聚合吞吐 = 并发 × 带宽 ÷ (权重 + 并发 × KV/请求)。
> **注意它是单调下降的**：上下文一长，聚合吞吐掉得比单请求速度还狠（8K → 128K 掉了 94%）。原因是并发拉高之后，KV 读取本身变成了主要搬运量——当并发足够大时，聚合吞吐会趋近于「带宽 ÷ 单请求 KV」，也就是 `3350 ÷ 1.07 ≈ 3 120`（8K）对 `3350 ÷ 17.2 ≈ 195`（128K）。
> 这就是长上下文场景下 **KV 量化、GQA、prefix caching 全都变得值钱**的原因：它们削的正是这项被迫的搬运。

---

## 6. 这些黑话，现在你能翻译了

**①「KV cache 爆了」**
= `batch × 上下文 × 每 token 字节` 超过了剩余显存。不是你模型装不下，是上下文装不下。

**②「显存还剩不少，怎么就 OOM 了」**
KV cache 是按请求动态分配的，长度不一的请求会让显存碎成拼不上的块。vLLM 的 PagedAttention 就是抄操作系统分页来解决这个，论文里吞吐提升 2–4×（[SOSP'23](https://arxiv.org/abs/2309.06180)）。**所以「换成 vLLM 快了很多」很多时候不是因为算法强，是因为不再浪费显存、能开更大 batch。**

**③「为什么现在都用 GQA」**
KV 头从 32 减到 8，KV cache 直接小 4 倍 → 同样的卡能开 4 倍长上下文或 4 倍并发。代价是注意力表达能力略降。这是**显存算术逼出来的架构设计**，不是学术趣味。

**④「prefix caching / RadixAttention」**
你有 RAG 或 Agent，每次请求前面都挂着同一段超长 system prompt / 工具描述 / 检索文档。这些前缀的 KV 每次都重算一遍纯属浪费——prefix caching 把它存下来复用。**对 Agent / RAG 场景，这可能是最便宜的一次性能升级**，因为它省的是 prefill（算力墙那边，第 3 课讲）。

**⑤「上下文军备竞赛」**
128K、1M 不是免费功能。它意味着你的显存预算里能塞的并发只剩个位数，或者要买 8 张卡。厂商宣传的是能力，你该算的是**并发和成本**。

## 7. 自测（先写答案，别翻上面）

**Q1.** Llama-3.1-8B（32 层、8 KV 头、head_dim 128、FP16）在 8K 上下文下，单个请求的 KV cache 约占多少显存？
A. 约 4 GB　B. 约 2 GB　C. 约 1 GB　D. 约 8 GB

**Q2.** 上下文从 8K 加到 32K，单请求 tok/s 为什么下降？
A. 每步多读 KV
B. 每步少读 KV
C. 每步多算权重
D. 每步少算权重

**Q3.** H100 80 GB、8B FP16（权重 16 GB）、32K 上下文，最多几个并发？
A. 约 24 个　B. 约 34 个　C. 约 59 个　D. 约 14 个

**Q4.** GQA 相比传统 MHA 的主要好处是？
A. 精度更高，效果更好一些
B. KV 更小，并发和上下文更大
C. 算力更省，预填充速度更快
D. 权重更小，单卡装更大模型

**Q5.** 显存「看着还够」却 OOM，最常见的原因是？
A. KV 碎片与预估不足
B. 驱动版本过于老旧
C. 显存带宽不够用了
D. 峰值算力被占满了

<details>
<summary>👉 对答案</summary>

1. **C**（约 1 GB）。8192 token × 128 KiB ≈ 1.07 GB。
2. **A**（每步多读 KV）。分母变成「权重 + KV」，不是算力问题。
3. **D**（约 14 个）。(80−16) ÷ 4.29 ≈ 14.9。
4. **B**（KV 更小，并发和上下文更大）。GQA 不是提精度，也不是省算力。
5. **A**（KV 碎片与预估不足）。这是动态分配 + 长度不一的必然产物。

</details>

## 8. 动手：扫一遍 4K → 128K（5 分钟）

打开 [`kv-cache-budget.xlsx`](../calculator/kv-cache-budget.xlsx)：

1. 在「显存预算」页把模型换成**你自己用的模型**——参数从 `config.json` 抄（层数、KV 头数、head_dim）

3. 找出「并发掉到 4 以下」的那个上下文长度——**这就是你这张卡的实际可用上下文上限**，不是模型标称的上限

## 9. 本机验证（Ollama 用户必做）

Ollama 默认上下文很小（通常 2K–4K）。试试显式加大：

```bash
# 加大上下文，观察显存与速度
ollama run qwen2.5:7b --verbose
>>> /set parameter num_ctx 32768
# 说一句长话，看 eval rate 和 nvidia-smi 里的显存变化
```

预期：**显存占用明显上升、eval rate 下降**。如果你能在 `--verbose` 里看到两个不同 `num_ctx` 下的 eval rate，把它们和速查文档第 4 节的表对一下——误差应该在同一量级。这就是「理论能预测实测」的第一次亲手验证。
