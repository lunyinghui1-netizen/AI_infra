## 0. 先把你和硬件人的词表对上

你已经在用硬件的**结果**了（Ollama 卡顿、vLLM 吞吐上不去、显存 OOM），只是不知道它在哪一层发生。对照一下：

| 你的说法       | 硬件人说             | 他其实在问什么                  |
| ---------- | ---------------- | ------------------------ |
| 模型多大？      | 参数量 P、权重显存       | 权重 GB = P × 每参数字节        |
| 上下文开多长？    | KV cache、seq_len | batch × 上下文 × 每 token 字节 |
| 这台机器能跑吗？   | 显存容量、OOM         | 权重 + KV cache + 激活 ≤ 容量  |
| 为什么这么慢？    | tok/s、TTFT、TPOT  | 时间 = 搬的字节 ÷ 带宽           |
| 能同时服务多少人？  | batch size、并发    | 显存款得下多少份 KV cache        |
| 换个更好的卡会快吗？ | 带宽 vs 算力、脊点      | 你现在撞的是哪堵墙                |

**注意最后一行的陷阱**：不是「更好的卡」就一定更快。这节课就是教你判断这件事。

## 1. GPU 里只有三样东西

忘了「晶体管」「流处理器」，暂时只需要三个格子：

```
       ┌──────────────────────────────┐
       │  显存 (HBM)   容量 GB         │   ← 装得下多少（模型 + KV cache）
       │       ↕  搬运通道 带宽 TB/s    │   ← 搬得快不快（决定 decode 速度）
       ┌──────────────────────────────┐
       │  计算单元 (SM + Tensor Core)  │   ← 算得快不快（决定 prefill、训练）
       │              算力 TFLOPS      │
       └──────────────────────────────┘
```

Horace He 的比喻很好记：**计算单元是工厂，显存是仓库，带宽是仓库到工厂的路**。工厂的产能（算力）这些年的增长，远远快过道路的运力（带宽）——所以大多数时候，工厂在等货。[（Brrrr From First Principles）](https://horace.io/brrr_intro.html)

`nvidia-smi` 里你能看到的那个「已用显存」，是仓库。而让你痛苦的 tok/s，是那条路。

---

## 2. 判定瓶颈的唯一标准：算术强度

给任何一件活，算两个数：

```
算术强度 = 做的浮点运算数 ÷ 搬运的字节数     （单位 FLOP/byte）
脊点     = 峰值算力 ÷ 峰值带宽               （单位 FLOP/byte）
```

- **算术强度 > 脊点** → 算力瓶颈：数据供得上，卡在算得慢。
- **算术强度 < 脊点** → **带宽瓶颈**：算力闲着，卡在搬得慢。

用 H100 算一下脊点（数字来自 [NVIDIA 官方 Hopper 文章](https://developer.nvidia.com/blog/nvidia-hopper-architecture-in-depth/)）：

```
990 TFLOPS ÷ 3.35 TB/s = 990×10¹² ÷ 3.35×10¹² ≈ 295 FLOP/byte
```

也就是说：**每秒搬进来的每 1 字节数据，得配上 295 次浮点运算，才配让这张卡「算满」。** 配不上，就是在等搬货。

这就是 [roofline 模型](https://dl.acm.org/doi/10.1145/1498765.1498785) 的全部精髓，用一张图表示就是两条线交叉：左边斜线是带宽天花板，右边水平线是算力天花板。

---

## 3. 为什么生成 token 永远撞带宽墙

现在算 decode：**每生成一个新 token，都要把模型全部权重从显存搬进计算单元一次。**

拿一个 8B 模型、FP16 精度（每个参数 2 字节）为例：

```
要搬的字节 = 8 × 10⁹ 参数 × 2 字节 = 16 GB
要算的运算 = 约 2 × 8 × 10⁹ ≈ 16 GFLOPs
算术强度   = 16 GFLOPs ÷ 16 GB = 1 FLOP/byte
```

**1 FLOP/byte，而脊点是 295 FLOP/byte。差了将近 300 倍。**

所以：

```
每个 token 的时间 ≥ 16 GB ÷ 3.35 TB/s ≈ 4.8 毫秒
单请求 tok/s    ≤ 3.35 TB/s ÷ 16 GB ≈ 209 token/秒
```

而这 4.8 毫秒里，计算单元真正干活的时间只有 `16 GFLOPs ÷ 990 TFLOPS ≈ 0.016 毫秒`——**不到 1%**。剩下 99% 的时间，990 TFLOPS 的卡在眼巴巴等显存发货。

这不是软件没优化好。任何人、任何框架，都突破不了 209 这个数。这就是硬件人说的 **memory-bound**（带宽瓶颈）。NVIDIA 自己的文档也是这么说的：decode 阶段「data is transferred to the GPU from memory dominates the latency」[（Mastering LLM Techniques: Inference Optimization）](https://developer.nvidia.com/blog/mastering-llm-techniques-inference-optimization/)。

### 把它变成一个公式（记住这一行就够）

```
tok/s 上限 ≈ 显存带宽 (B/s) ÷ 权重字节数 (B)
          = 显存带宽 ÷ (参数量 × 每参数字节)
```

而 prefill（处理你的 prompt）恰恰相反：那是矩阵乘矩阵，一次算一大片，算术强度高，是算力瓶颈——所以「长 prompt 首 token 慢」和「生成慢」是两个不同的墙，用不同的办法治（第 5 课讲 TTFT）。

## 4. 把公式用五次（练习时间，别跳过）

盖住右边两列，自己先估，再对答案：

| 场景                           | 权重显存    | 理论上限 tok/s |
| ---------------------------- | ------- | ---------- |
| 8B FP16，H100（3.35 TB/s）      | 16 GB   | **209**    |
| 8B FP16，A100 80G（2.04 TB/s）  | 16 GB   | **127**    |
| 8B **INT8**，H100             | 8 GB    | **419**    |
| 70B FP16，H100 两张（TP=2，每卡扛一半） | 70 GB/卡 | **48**     |
| 8B FP16，RTX 4090（1.01 TB/s）  | 16 GB   | **63**     |

**自己核对第 2 行和第 5 行**：4090 的 tok/s 是 A100 的一半，但它的算力（约 165 vs 312 TFLOPS）也就一半——碰巧差不多；可它跟 H100 比是 1/3.3，算力却只有 1/6。

**结论**：拿「TFLOPS 大小」来买推理卡，是外行挑选方式。**先看带宽，再看容量。**

## 5. 三个立刻能用的推论（这就是「黑话」的翻译）

**① 「量化能加速」——为什么？**
把每参数字节从 2 降到 1，分母减半 → tok/s 理论上翻倍（8B 从 209 → 419）。同时显存占用也减半。**量化的第一条收益是省带宽，第二条才是省显存。** 这也解释了为什么量化对 decode 帮助巨大、对训练几乎没帮助（训练是算力瓶颈）。

**② 「加大 batch 提吞吐」——代价是什么？**
同一份 16 GB 权重，搬一次可以同时服务 B 个请求（batch=B）。搬运成本被摊薄 B 份 → **聚合吞吐 ≈ B × 209 tok/s**，直到算术强度 `2×B÷2 = B` 超过脊点 295 为止（也就是 batch 到 300 左右开始变成算力瓶颈）。
但每个请求还得等那 4.8 毫秒 → **单请求速度不变（甚至略变差）**。所以「吞吐」和「延迟」天生对立。云厂商卖的便宜 API，背后就是大 batch。

**③ 「上 TP=8 能跑更大的模型」——为什么单请求也变快了？**
70B FP16 是 140 GB，一张 80 GB 卡装不下。切成 TP=2 后每张卡只管 70 GB 权重，只需搬自己那份 → 单请求速度 ≈ 48 tok/s，接近「一张卡搬 70 GB」的速度。**卡多了，每张卡要搬的东西少了。**
但代价开始了：每层算完要跟另一张卡同步数据，网络带宽成了新的墙（第 6 课）。所以 TP 不是越多越快的免费午餐。

<summary>👉 点开对答案（先自己写完再看）</summary>

1. **B**（2 字节）。所以权重 GB ≈ 参数量(B) × 2。
2. **C**（约 209 tok/s）。3.35×10¹² ÷ 16×10⁹ ≈ 209。A 是「不会算」的猜法，D 是把算力当带宽了。

5. **A**（大约翻倍）。分母从 2 字节降到 1 字节。真机上因 KV cache 读取和 kernel 效率，通常拿不到 2×。

## 7. 动手：用 Excel 计算器把自己的场景算一遍（5 分钟）

打开 [`gpu-throughput-calculator.xlsx`](../calculator/gpu-throughput-calculator.xlsx)，只改**黄色格子**：

3. 你机器 / 云实例的**显存带宽**（查 `gpu-numbers.md`，或搜你的卡型号 + "memory bandwidth"）
4. 显存容量、上下文长度、并发数

然后看输出区的四个数：**理论 tok/s、脊点、瓶颈判断、显存够不够、最多能扛多少并发**。

## 8. 可选但强烈建议：在本机验证一次

如果你本地的 Ollama 能跑（`ollama run qwen2.5:7b`），加 `--verbose` 会打印 **eval rate（tok/s）**。

```
实测 tok/s ÷ 你的理论上限 ≈ 50% ~ 80%
```

差额来自：KV cache 读取、kernel 效率、采样开销、Python 开销。**实测比理论低是正常的，比理论高是不可能的**——如果你算出来「实测 > 理论」，那一定是规格或参数搞错了（这本身是很好的学习时刻）。

把这两个数发我，我们把差值拆开，你就知道自己那张卡的效率水平了。
